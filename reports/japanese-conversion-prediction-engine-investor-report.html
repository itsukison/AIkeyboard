日本語変換・予測エンジン 技術概要

投資家向け技術ブリーフ｜実装確認日 2026年7月26日｜対象：通常の日本語入力（AI文章書き換え機能は別系統）

要点：通常入力は、ローマ字／フリック入力から候補表示、学習、次語予測まで端末内で完結する。辞書型の高速変換を土台に、軽量ニューラルモデル「Zenzai」で文脈を考慮し、利用者自身の選択履歴と端末内コーパス表で個人化する。入力中の文字をサーバーへ送らないため、通信遅延・圏外・プライバシーの影響を受けずに基本機能が動く。

1. 入力から確定まで、何が起きているか

キー入力 → かな生成 → 候補探索・順位付け → 候補表示 → ユーザー確定 → 学習・次語予測
  1. 入力を受け取る。QWERTYでは英字を小文字化してローマ字バッファへ、12キーではかなを直接バッファへ入れる。未完成の末尾（例：「きょうk」のk）は候補探索から外しつつ、画面にはそのまま見せる。
  2. かなを即時表示する。解決できたローマ字を逐次かなに変え、iOSの「未確定文字（marked text）」として入力先アプリへ表示する。変換候補を待たないので、キー入力の反応が先に返る。
  3. 毎入力で非同期変換する。状態管理の InputManager が、AzooKeyKanaKanjiConverterを包むactorへ変換を依頼する。古い処理はキャンセルし、同じかな部分なら再計算を省く。
  4. 候補を安全に提示する。上位20件を横スクロールで表示し、展開時だけ全候補を読み出す。空白キーは候補を順番に選ぶ。ユーザーが選択を始めた後は候補配列を固定し、遅れて届いた結果でタップ対象が動かないようにする。
  5. 見えている文字だけを確定する。候補タップ、または空白で選んだ候補を確定する。何も選ばずReturnを押した場合は、先頭の漢字候補を勝手に採用せず、表示中のかなを確定する。

2. 変換精度を作る二層構造

土台＝辞書・ラティス変換。AzooKeyの標準辞書、タイプミス補正、入力途中の日本語予測を利用する。成熟したOSSを採用することで、辞書整備と日本語の分かち書きをゼロから再実装せず、アプリ固有の操作性・安全性・個人化に開発を集中できる。

上積み＝Zenzai。20MBの zenz-v3.1-xsmall をCPU上で動かし、古典変換だけでは曖昧な候補を文脈込みで評価する。入力開始時にカーソル左側の文脈を一度取得し、直近部分だけを使うため、精度改善と計算量の上限を両立する。推論回数は2回に抑え、品質と待ち時間の均衡を取った。

3. 予測変換と「使うほど合う」仕組み

単語を確定した直後、最大10件の次語候補を次の優先順で統合し、重複を除いて表示する。

  1. 本人の履歴：「この語の次に何を確定したか」を端末内App Groupへ保存。頻度が高いものを優先し、同数なら最近使ったものを上位にする（最大2,000遷移）。結果は即時表示できる。
  2. 3-gram表：直前2形態素から次の形態素を予測。FineWeb-2の日本語Webコーパスからオフライン生成した約12MBの表で、文脈を絞り込む。
  3. AzooKeyの予測：確定候補が持つ品詞・形態素情報と適応学習を使う。候補をタップすると学習へ戻し、次の予測にも文脈を連結する。
  4. 2-gram表：直前1形態素からの約10MBの表で、3-gramやAzooKeyが不足する場合を補う。

変換候補を確定した結果はAzooKeyの入力・出力学習へ渡し、同じ読みや関連表現の順位を改善する。メモリ内学習は最大5,000件に制限し、ディスク統合は入力中ではなくキーボード終了時に行う。これにより、タイピング中の引っ掛かりを避けながら長期学習を残す。

4. 主な設計判断と、その理由

  • 変換は完全ローカル：基本入力を通信・ログイン・Full Accessの有無から切り離し、速度、可用性、信頼を守る。Cloud AIはユーザーが明示操作した文章書き換えだけの別機能。
  • デバウンスなし：かな表示は即時、変換器は差分ラティスを延長でき、actorが直列化する。待ち時間を人工的に足すより、古いタスクを捨てて最新候補を早く出す方がUXに合う。
  • 変換器はプロセスに1個：iOSはキーボード画面を作り直しても拡張プロセスを残すことがある。コントローラごとに辞書／llamaコンテキストを持つとメモリが積み上がるため、共有インスタンスだけを使う。
  • CPU専用の自社fork：上流のMetal付きllamaバイナリはキーボード拡張でモデル読込時に異常終了したため、Metalを外した ZenzaiCPU を固定採用した。
  • 予測表はメモリマップ：大きな2-gram／3-gram全体をRAMへ展開せず、二分探索で必要ページだけ読む。常駐メモリを抑える代わりに、アプリ容量は約23MB増える。

5. 制約・残るリスク

最大の制約はiOSキーボード拡張のメモリ上限。端末・ホストアプリにより上限が変わり、超過するとiOSがプロセスを終了する。目標は40MB未満。Zenzaiは古典変換に加えて約25MBの一時的な余裕を要するため、利用可能メモリが50MB以下なら自動的に古典変換へ戻す。
  • 速度保護：最初の3回を除く15回の中央値が150msを超えると、そのプロセスではZenzaiを停止し、同一ビルドでは設定を保持する。低電力モードや高温時の遅さは端末性能判定に使わない。
  • 起動保護：辞書だけを先に準備し、Zenzaiの重み読込と初回推論はキーボード表示後に遅延実行する。初画面と重いモデルロードを競合させない。
  • 予測データの限界：FineWeb-2由来の表は2013〜2024年のWeb傾向を反映する静的データで、最新語や専門語は再生成または利用者学習が必要。Webコーパス固有の偏りも残り得る。
  • ホスト依存：入力先アプリが文書を外部操作で消去した場合は未確定状態を破棄するなど防御しているが、取得できる周辺文脈とmarked textの挙動はiOS／ホストアプリのAPI制約を受ける。
  • 公開前確認：実機（旧端末を含む）で、変換・候補展開・AIオーバーレイを通した40MB未満のピーク確認が未完了の本番準備項目である。

投資家向け総括：本エンジンの競争力は、既存の高品質OSSを基盤にしながら、端末内ニューラル変換、個人学習、独自の次語コーパス、iOS拡張向けのメモリ防御を一つの入力体験に統合した点にある。品質を上げる機構と、遅い・メモリが少ない端末でも落とさず動かす機構が同時に設計されている。
