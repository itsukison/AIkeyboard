# SEO / GEO — keigobutton.com

(`web/` in the repo). ASO lives in `research/jp-market.md`; this file owns the

## 結論

**勝てるのは「ツール意図」のクエリ群。負けるのは「フレーズ解説」のクエリ群。**
`敬語変換` `敬語チェック` `敬語テスト` のSERPは小規模ツールサイトと個人サイトが
占めており、新規ドメインでも入れる。一方 `「了解しました」言い換え` 系は
マイナビ・楽天・アメックス・タウンワークが埋めており、当面入れない。
GEO（llms.txt）は競合ゼロで、いま置くだけで先行できる。

## 前提の修正（2026-08-16）— デスクトップ版マージによる後退

2026-08-08 のデスクトップ版マージ（`a4e23bc`）で **`/` の中身がMac版ランディングに
置き換わり、iPhone版が新規URL `/mobile` へ退避した**。実測した被害は3つ。

| 事象 | 実測（2026-08-16、Search Console API） |
|---|---|
| ブランドクエリの後退 | `敬語ボタン` → `/` が **7/28–31は掲載順位4.0・1日4クリック**。マージ後は 7.7 → 9.5 → 7.5 で **クリック0**。28日集計は 15クリック / 65表示 / 5.1位 |
| iPhone版の消失 | `/mobile` は **`検出 - インデックス未登録`、`lastCrawlTime: null`**。8日経ってGoogleが一度も取得していない。表示回数 **0** |
| 内部ハブの切断 | ホームからのツール・ハブへのリンクが **5本 → 2本**。失ったうちの `/keigo-check` は **当サイト最大の表示回数（139表示・9.1位）** |

`/en` も同じく未クロール、`/zh` はURLの存在すら認識されていない。

**原因は「単一プラットフォームのページがブランドURLを占有したこと」。** `/` の
`crawledAs` は `MOBILE`（実測）で、`敬語ボタン` を検索するのは大半がiPhone版を
探すスマホ利用者。そこに 「敬語ボタン **Mac版**」 という title を返していた。
調査した同種プロダクト（Notion `/desktop`・`/mobile`、1Password `/downloads/mac`、
Grammarly `/desktop`、Raycast、Superhuman、Obsidian）は **例外なく `/` をブランドの
ハブにして、プラットフォーム別ページを1階層下に置いている**。

### 対応（2026-08-16 実装済み）

**デザインは変更していない。**Mac版の見た目は一切触らず、URL・メタデータ・
内部リンク・構造化データのみを直した。

- **`/` の title をブランド起点に差し替え**。「敬語ボタン｜Mac・iPhoneで文章をその場で敬語に」。
  h1（「いま書いている場所で、そのまま整える。」）は**意図的に据え置き**——変更すると
  Mac版のデザインに手を入れることになるため。ブランド名がh1に無い状態は残課題（下記）
- **`/mobile` → `/iphone`（308）**。未クロールで失うものが無いうちに直した。`/mobile` は
  Googleが「別URL方式のモバイルサイト」として文書化しているURL形なうえ、実体は
  iPhone版の**製品ページ**であってサイトの端末別バリアントではない。`/iphone` は
  クエリ文字列（「敬語ボタン iPhone」）とも一致する
- **内部ハブを復旧**。Mac版フッターのナビ列に `/keigo-check` `/keigo-test` `/reibun` を
  追加し、法務リンク列に `/support` を追加（`/en/support` `/zh/support` は
  sitemapにあるだけで被リンク0の孤児だった）。`Footer.jsx` にその旨のコメントを残した
- **JSON-LD を言語別に生成**（`lib/site.ts` → `macSoftwareApplicationNode(lang)`）。
  従来は `/en` でも `inLanguage: "ja"`・日本語の `description`・`priceCurrency: "JPY"` を
  出力しており、**同ページの料金表がドル建てで表示されているのと矛盾していた**
  （`pricing.js` の `currencyFor` は `en → usd`）。`websiteNodeFor(lang)` も同様
- **`llms.txt` を再構成**。「アプリ」節を Key facts の直後へ繰り上げ（従来は無料ツールと
  記事16本の下だった）、`## English` ブロックを追加。**別ファイルにはしない**——
  llmstxt.org に多言語の規約は無く、2つ置けば必ず片方が腐る（§設計方針14）

### 検索面での帰結 — これが表示回数が伸びない本当の理由

28日間の全クエリは **28件**。うち2件（`敬語チェック` `敬語ボタン`）で表示回数の **83%**。
そして **`敬語チェック` は平均掲載順位9.3（1ページ目）で28日116表示 = 1日約4回**。
これは「1ページ目に居るときの表示回数 ≒ そのクエリの実需要」なので、
**このキーワードの実サイズを自社データで直接測ったことになる。月100〜300回規模。**

つまり順位の問題ではない（表示の190/225が既に4〜10位）。

同時に上限でもあった。

1日1,000表示は、この測定値では **上位10位のクエリが約250件**必要。現在28件。
くさびだけでは到達しない（A+B群を全部1位にしても1日100〜300が上限）。
必要なのは3本柱: ①くさび（維持・CVは高い）②カテゴリ（未着手）
③場面別ロングテール（74〜95位に滞留、ボリュームは実在）。

## 設計方針 — なぜこう作ったか

新しいページを追加する前にここを読む。個々のキーワードは動くが、この判断基準は動かない。

### SEO側の方針

**1. 検索ボリュームではなく「SERPの顔ぶれ」で狙う場所を決めた。**
ツールなしでボリュームを推定するより、実際にSERPを引いて上位10件の権威を見るほうが
新規ドメインには正確。`敬語変換` の上位は Canva・3秒敬語・keigoai.com・個人ツールサイト、
`「了解しました」言い換え` の上位はマイナビ・楽天・アメックス・タウンワーク。
**前者には入れて後者には入れない。**これが全体の設計を決めた唯一の判断。
ボリュームが太いことは、勝てることを意味しない。

**2. 記事よりツールを先に作った。**
理由は3つ。①ツールページは滞在時間・再訪・被リンクを自然に生む。記事は読まれて終わる。
②競合（3秒敬語・LeapMe）がどちらもツールを先頭に置いて成功している——観測された勝ち筋を
再実装するほうが安全。③ツールは「使わせてから入れさせる」導線が作れる。記事はCTAが弱い。

**3. 1ページ = 1クエリクラスタ。**
`keyword`（主軸）を title と h1 に置き、`alsoRanks`（周辺クエリ）は本文で自然に回収する。
1ページに複数の主軸を詰めるとどちらも中途半端になる。`content/*.ts` の型がこの規律を
強制している（`keyword` は単数、`alsoRanks` は配列）。

**4. コンテンツを型付きデータとして書いた（`content/`, `lib/blocks.ts`）。**
SEOコンテンツの典型的な失敗は、本文・構造化データ・サイトマップ・要約が時間差で乖離すること。
1つのソースからページ本文・JSON-LD・sitemap・llms.txt を生成すれば、**構造上乖離できない**。
記事を1本足せば sitemap と llms.txt に自動で載る。手で同期する運用にはしない。

**5. 内部リンクをハブ&スポークで組んだ。**
新規ドメインに外部被リンクは無いので、動かせるのは内部リンクだけ。
ホーム → ツール3本・ハブ2本（`FaqLinks`）、ツール ↔ 記事 ↔ 例文を相互に。
**ホームからのリンクは特に重要**なので `app/page.tsx` にその旨のコメントを残した
（デザイン変更で消されると効果が落ちるため）。

**6. 変換ページでも「読んで終わる人」に答えを出した。**
`/keigo-henkan` はツールをファーストビューに置くが、その下に4モードの使い分け・手順・
変換例・FAQ を書いている。ツールを使わなかった訪問者にもクエリの答えを返す本文がないと、
検索エンジンから見て薄いページになる。ツールだけのページは順位が付かない。

**7. 不利な事実を自分から書いた。**
比較記事に「この記事は敬語ボタンの運営が書いている」「レビュー件数は3秒敬語が
当社を大きく上回る（559件対8件）」「機能の広さではLeapMeが上」を明記した。
理由は2つ——景表法・ステマ規制の観点で運営者表記が必要であること、そして
比較記事の信頼性が競合を貶さないことで担保されること。他社情報はすべて
**日付を添えた**（料金とレビュー件数は動くため）。

**8. 勝てない場所を明示的に捨てた。**
`「了解しました」言い換え` 等の単語解説系は上位が固定されている。ここに書くと
工数が消えるだけなので、方針として「当面取りに行かない」を文書化した（§D）。
知識記事（`/blog/niju-keigo` 等）はこの層の周辺だけ拾い、主目的はテスト・チェックへの内部導線。

### GEO側の方針

**9. `llms.txt` と `llms-full.txt` は役割が違う。**
前者は**索引**——アシスタントが「どのURLを取りに行くか」を決めるためのもの。
後者は**本文コーパス**——約20ルートをJSレンダリングして巡回させる代わりに、1フェッチで
全文を渡すためのもの。両方置くのは冗長ではなく、取得段階が2つあるから。

**10. `Key facts` ブロックが llms.txt の本体。**
「iPhoneで敬語に変換できるキーボードは？」に答えるとき、モデルが必要なのは
宣伝文ではなく**帰属可能で検証できる事実**。名称・運営・対応OS・料金・機能・
プライバシーの扱いを、1行ずつ確認できる形で並べた。文章ではなく事実の列挙にしている。

**11. 制約をこちらから書いた。**
iOS限定であること、フルアクセス許可が必要であること、レビュー件数が競合より
桁で少ないこと、長文ならChatGPTのほうが適することを明記した。
理由は2つ——**LLMは比較を求められると一方的な自社称賛を割り引く**ため、
制約を書いたほうが引用されやすい。そして書かなければ単に誤情報になる。

**12. 比較の答えを先に用意した（`他サービスとの違い`）。**
モデルに競合ページから差分を合成させると、結論はこちらの制御外になる。
3秒敬語・LeapMe・ChatGPT・Webツールとの違いを**自分で、公平に**書いておけば、
その記述が引用候補になる。公平でないと採用されないので、公平さが実利になる構造。

**13. リンクの説明文を「狙うクエリへの回答」として書いた。**
`- [敬語チェック](url): 二重敬語や誤用を判定し、言い換え候補を表示します。判定は
ブラウザ内で完結するため入力文は送信されません。` のように、説明を読んだだけで
そのページが何に答えるか分かる形にした。全URLをフェッチせずに選別できる。

**14. llms.txt もレジストリから生成した。**
ページ本文と llms.txt が矛盾していると、それを検出したモデルはソース全体の信頼度を
下げる。同一ソースから生成すれば矛盾しない。手書きの llms.txt は必ず腐る。

**15. クローラー許可を明示した（33種）。**
未記載でも既定は許可だが、`Applebot-Extended` と `Google-Extended` は

### 検証の方針

**17. 主張する前に実際に叩いた。**
- ルールベース判定29件：正しい敬語8文で誤検知ゼロ、期待する15件すべて発火、
  複数回実行で同一結果（正規表現の `lastIndex` リーク無し）を確認
- エッジ関数：許可/不許可オリジン、300文字超、空文字、プリフライト、
  1日5回上限→429 をすべて本番で確認
- 掲載する変換例：**全件を実エンドポイントに通した**

**18. 「り。」の件が方針になった。**
`/keigo-henkan` に「り。」→「承知いたしました。」を掲載していたが、実際に叩くと
Web版（Cerebras）は「りです。」を返した。若者スラングを解釈できていない。
**ページ上のツールが自分の掲載例を再現できない状態は、地味な例を出すより信用を損なう。**
掲載例4件すべてを実出力に差し替えた。以後、掲載例を編集するときは必ず実行して確認する。

### やらなかったこと（意図的）

- **AIによる文章の大量生成**。19ページすべて中身を書いた。薄い量産ページは
  ドメイン全体の評価を下げるほうに効く
- **`/keigo-check` をAI化**しなかった。ルールベースだから「送信しない」と約束でき、
  それがこのページの差別化そのもの。AIにすると約束が壊れる
- **単語解説記事の量産**。§D の通り勝てないので着手しない
- **被リンク購入・相互リンク**。検討していない
- **`supabase db push`**。リモートのマイグレーション履歴がローカルと不一致のため、
  新規1件のみを個別適用した（§再デプロイ手順の警告を参照）

### 新しいページを追加する手順

上の方針を実務手順に落としたもの。1〜3を飛ばして書き始めないこと。

1. **SERPを実際に引く。** 狙うクエリで検索し、上位10件の顔ぶれを見る。
   大手メディア・転職メディアが4件以上なら**書かない**（§D行き）。
   小規模サイト・ツールサイト中心なら着手する。
2. **主軸クエリを1つ決める。** 周辺クエリは `alsoRanks` に入れる。
   主軸が2つ思い浮かんだらページを2枚に分ける。
3. **§キーワードマップの表に行を足す。** 着手前に足す。書いてから足すと表が腐る。
4. **`content/articles.ts` か `content/reibun.ts` にデータとして書く。**
   JSXを直接書かない。`Block[]` で表現できない構成が必要になったら
   `lib/blocks.ts` に型を足し、`Prose` と `blocksToText` の両方を対応させる
   （片方だけだと llms-full.txt が壊れる）。
5. **`faq` を3件以上書く。** 理由は**LLMが引用する単位になること**（GEO側）。
   質問は実際に検索されている形（「〜は無料ですか」「〜と何が違いますか」）にする。
   **リッチリザルトは期待しない**——Googleは2023年8月にFAQリッチリザルトを
   政府・医療系の権威サイトのみに限定し、HowToは完全に廃止した。2026-07-30 の
   URL Inspection API 実測でも、検出されたリッチリザルトは**パンくずリストのみ**
   （インデックス済みの対象9ページすべてで検出、ホームは設計通り対象外）。
   FAQPage / HowTo / Quiz は1件も報告されない。マークアップ自体は有害ではなく
   GEO資産として残すが、SERP上の見返りを理由に書かないこと。
6. **内部リンクを最低2本。** 関連ページへ（`related`）と、ツールへ（`tool` ブロック）。
7. **他社に言及するなら日付を添える。** そして不利な点も書く。
8. **主張を実際に確認する。** 変換例を載せるならエンドポイントに通す。
   ツールの挙動を書くなら動かす（§設計方針18）。
9. **`npm run build`** が通ること。sitemap と llms.txt は自動更新される——
   手で足す必要はないし、足してはいけない。

  -H 'Content-Type: application/json' -H 'Origin: https://keigobutton.com' \

> **`supabase db push` は使わないこと。** リモートのマイグレーション履歴の
> version がローカルのファイル名と一致していない（名前は同じだがタイムスタンプが
> 別物。`harden_function_grants` はリモート履歴に存在しない）。`db push` は
> version 文字列で比較するため、ローカル10件すべてを未適用と判断して再実行する。
> 大半が `if not exists` / `or replace` なので事故にはなりにくいが、賭ける価値はない。

## 計測スクリプト

Search Console API に**サービスアカウント**で接続している（OAuthブラウザフローなし、
第三者MCPにGSC権限を渡していない）。認証は標準ライブラリ＋`cryptography` で
JWTを自前署名しており、`google-auth` 依存は無い。

```bash
export GOOGLE_APPLICATION_CREDENTIALS=~/.config/keigobutton/gsc.json
export GSC_SITE_URL=sc-domain:keigobutton.com
cd web
python3 scripts/gsc.py sites             # プロパティと権限レベル
python3 scripts/gsc.py sitemaps          # 送信状況・エラー数・検出URL数
python3 scripts/gsc.py inspect <url>     # URL単位の詳細
python3 scripts/gsc.py analytics 28      # クエリ×ページ
python3 scripts/gsc-weekly.py            # 全URL一括＋前回スナップショットとの差分
```

`gsc-weekly.py` は**URL一覧を本番のsitemapから取る**ので、記事を1本足せば
そのまま計測対象に入る（sitemap.ts と同じ「手で同期しない」方針）。
スナップショットは `web/scripts/gsc-snapshots/<date>.json` に残り、
次回実行時に「discovered → indexed」の遷移だけを差分表示する。

サービスアカウント（`keigobutton@keigobutton.iam.gserviceaccount.com`）は
GSCの**「フル」ユーザー**として追加してある。「制限付き」では
URL Inspection API が 403 になるため下げないこと。

## 測定

Search Console接続後、週次レビュー（`weekly-review.md`）に以下を追加する。
インストール数だけで評価しないこと——ツールページは「使われてから入れる」導線なので、
順位とクリックが先に動く。

| 層 | 指標 | 見方 |
|---|---|---|
| 露出 | インデックス数 / 表示回数 | 19ページが入り切っているか |
| 順位 | 上表A・B群の平均掲載順位 | Aから先に動くはず |
| 流入 | ページ別クリック数 | どのクラスタが太いか |
| 行動 | `/keigo-henkan` の変換実行率、1日5回の到達率 | 到達率が高いほどインストール導線が効く |
| 転換 | ページ別 App Store リンククリック | 比較記事（B群）が最も高い想定 |
| GEO | ChatGPT / Perplexity / Google AIO で自ブランドが出るか | 月1回、手動で主要10クエリを叩く。先行指標として `/llms.txt` へのAIクローラーUAをVercelログで週次確認（§未実施 9） |

`web-rewrite` は `console.error` のみで成功ログを出していない。変換実行率を
測るなら PostHog のクライアントイベントを `/keigo-henkan` に足すのが軽い。
